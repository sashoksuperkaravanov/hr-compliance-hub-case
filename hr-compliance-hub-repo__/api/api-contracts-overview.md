# API-контракты: пояснения и обоснование решений

**Файл спецификации:** [`openapi.yaml`](openapi.yaml) (OpenAPI 3.1, провалидирован `openapi-spec-validator`)

---

## 1. Что входит в контракт, а что нет

В спецификацию включены только **REST-эндпоинты, реально экспонируемые Hub'ом наружу**:
- `POST /v1/webhooks/edo-status` — приём статуса от оператора ЭДО (FR-07)
- `GET /v1/documents*` — журнал для Compliance-офицера (UC8, FR-11, FR-13)
- `GET/PUT /v1/config/retry-policy` — конфигурация retry (UC9, FR-12)

**Не включено:** обмен `HRM ↔ Hub` и `Hub ↔ система расчёта ЗП`. Это событийное взаимодействие через Kafka (см. Component Diagram), а не REST-вызов, и формат сообщений шины — предмет отдельного артефакта (JSON Schema для событий), не OpenAPI. Также не специфицирован полный контракт исходящего вызова `Hub → Оператор ЭДО` (`Task_Send`/`Dispatch Service`): это контракт **внешней** системы, которым Hub является потребителем, а не владельцем. Его точный формат согласовывается с оператором отдельно (см. открытый вопрос №2 ниже).

## 2. Закрытие открытого вопроса №2 (частично)

Открытый вопрос №2 («Согласование формата correlation-id/idempotency-key с реальным API оператора ЭДО») закрывается на уровне **входящего** контракта: `EdoStatusWebhookPayload.correlation_id` — обязательное поле, равное `HRDocument.correlation_id` из ER-модели. Это фиксирует внутреннее решение Hub'а.

Открытым остаётся вопрос, примет ли реальный оператор ЭДО этот же correlation_id как сквозной идентификатор в своём API, или потребуется маппинг на его собственный формат идентификатора транзакции. Это по-прежнему требует согласования с конкретным оператором и не может быть закрыто внутренней документацией.

## 3. Ключевые решения и их обоснование

### 3.1. Идемпотентность webhook на уровне контракта, не только описания

`WebhookAck.duplicate` делает идемпотентность видимой в ответе, а не скрытой деталью реализации. Это позволяет оператору ЭДО (и тестировщику) убедиться, что повторная доставка обработана корректно, не заглядывая в журнал Hub'а. Так реализуется NFR-05 на уровне наблюдаемого поведения API, а не только внутренней логики.

### 3.2. `PUT /v1/config/retry-policy` создаёт новую версию, а не перезаписывает

Согласовано с решением в ER-модели ([`data-dictionary.md`](../docs/data/data-dictionary.md)): таблица `RetryPolicyConfig` версионируется. В description эндпоинта явно указано, что изменение не влияет на уже запланированные retry по документам в очереди. Это важное бизнес-правило: иначе изменение политики "задним числом" непредсказуемо повлияет на уже идущие ретраи.

### 3.3. Отдельный `mTLS` для webhook-эндпоинта, `Bearer JWT` для остального

Входящий webhook от оператора ЭДО — межсистемное взаимодействие без участия человека, поэтому аутентификация через клиентский сертификат (mTLS) естественнее, чем токен, и напрямую поддерживает NFR-07 (контроль срока действия сертификата). Человеко-инициированные вызовы (`/v1/documents*`, `/v1/config/*`) используют JWT с claim `role`, реализующим RBAC (NFR-08).

### 3.4. 404 на webhook — телеметрия инцидента, а не ошибка клиента

`POST /v1/webhooks/edo-status` при неизвестном `correlation_id` возвращает 404, но в описании явно указано: это соответствует исключению **E3** из Use Case Spec (карантинная очередь, уведомление ИТ-администратора), а не стандартной трактовке "ресурс не найден, вызывающий ошибся". Разработчик, реализующий обработку 404, должен учитывать, что здесь нужна отдельная логика (dead-letter queue), а не простое игнорирование.

### 3.5. Классификация статуса в `EdoStatusWebhookPayload`: три значения, не два

`status: confirmed | rejected_technical | rejected_content` напрямую отражает классификацию FR-06 и правило BR-01 (технический отказ → retry, содержательный → немедленная эскалация). Разделение выполняется на входе в Hub, а не после: контракт webhook явно требует от оператора ЭДО присылать эту классификацию, а не просто "успех/неуспех".

## 4. Что осталось вне контракта

- Формат исходящего пакета документов в СФР (форма ЕФС-1) — контракт **оператора ЭДО**, не Hub'а; Hub передаёт данные в формате, который определит оператор при интеграции.
- Rate limiting и конкретные HTTP-заголовки (`X-RateLimit-*`) — техническая деталь реализации, не предмет аналитического контракта на этом этапе.
