**Система:** HR Compliance Hub
**Компания:** МеталлИнвестХолдинг

## UC3 + UC5 — Сформировать и отправить пакет оператору ЭДО (с повторной отправкой)

| Поле | Значение |
|---|---|
| **ID** | UC3 |
| **Название** | Сформировать и отправить пакет оператору ЭДО |
| **Уровень** | Пользовательская цель (user goal), реализуется системным актором |
| **Первичный актор** | HR Compliance Hub (инициирует автоматически) |
| **Вторичные акторы** | Оператор ЭДО, СФР (косвенно, через оператора) |
| **Заинтересованные стороны и их интересы** | Кадровый специалист: заинтересован в отсутствии ручных действий. Compliance-офицер: заинтересован в соблюдении регуляторных сроков. ИТ-администратор: заинтересован в предсказуемой нагрузке на очередь сообщений |

### Предусловия
- Кадровый документ успешно прошёл валидацию (UC2) — состояние `Validating` завершилось положительным исходом (см. State Diagram: [источник](../process-models/state-diagram.puml) · [PNG](../process-models/state-diagram.png)).
- Сформирован пакет данных, соответствующий формату, ожидаемому оператором ЭДО (JSON/XML-схема согласно API-контракту оператора).
- Учётные данные для аутентификации на стороне оператора ЭДО актуальны (сертификат ЭЦП не истёк).

### Триггер
Данные документа признаны валидными по итогам UC2 (переход `Validating → SentToOperator` в State Diagram) **или** истёк интервал ожидания по правилу retry (см. Основной поток, шаг 7; в State Diagram — переход `RetryScheduled → SentToOperator`).

> **Примечание:** терминология приведена к единому источнику истины — состояниям State Diagram (ранее использовались статусы «Черновик подтверждён» и «Готов к отправке», не имевшие формального соответствия).

### Основной поток событий

1. Hub формирует пакет документов в формате, ожидаемом оператором ЭДО, включая XML-подпись (усиленная квалифицированная ЭП организации).
2. Hub присваивает документу статус `Отправлен оператору` и записывает временную метку отправки в журнал.
3. Hub вызывает API оператора ЭДО (синхронный HTTP-запрос на приём пакета).
4. Оператор ЭДО возвращает синхронное подтверждение приёма пакета в обработку (не путать с подтверждением от СФР — это лишь подтверждение получения запроса).
5. Hub присваивает документу статус `Передан в СФР` (ожидание асинхронного результата — см. UC4).
6. Use case завершается успешно; управление передаётся в UC4 (ожидание статуса).

### Альтернативный поток A1 — недоступность оператора ЭДО (шаг 3)

- A1.1. Запрос к API оператора ЭДО завершается таймаутом или кодом 5xx.
- A1.2. Hub классифицирует ошибку как **техническую** и инициирует правило retry (см. UC5 ниже).
- A1.3. Возврат к шагу 3 основного потока согласно расписанию retry.

### Расширение UC5 — Выполнить повторную отправку (retry)

*Активируется как `<<extend>>` UC3 при возникновении технического сбоя (A1) либо при получении от СФР технического отклонения (см. UC4, альтернативный поток A2).*

**Бизнес-правило BR-01 (retry-политика):**

| Параметр | Значение |
|---|---|
| Максимальное количество автоматических попыток | 3 |
| Интервал перед 1-й повторной попыткой | 5 минут |
| Интервал перед 2-й повторной попыткой | 30 минут |
| Интервал перед 3-й повторной попыткой | 2 часа |
| Действие после исчерпания попыток | Эскалация кадровику (UC6) |
| Условие применения | Только для **технических** сбоев (таймаут, недоступность сети, HTTP 5xx). Содержательные отклонения (например, СНИЛС не найден в реестре ПФР) retry не подлежат — эскалируются немедленно. |

1. Hub увеличивает счётчик попыток документа на 1.
2. Hub проверяет: счётчик попыток ≤ 3?
   - Да → Hub планирует повторную отправку через соответствующий интервал (Delayed Message / Scheduled Task в очереди) → возврат к шагу 3 UC3.
   - Нет → передача управления в UC6 (эскалация).
3. Каждая попытка логируется в журнале аудита с указанием причины предыдущей неудачи (для последующего разбора Compliance-офицером).

### Исключения

- **E1.** Оператор ЭДО возвращает код 4xx (ошибка в самом запросе — некорректный формат, истёкший сертификат ЭЦП). Это **не** технический сбой в смысле BR-01 — Hub немедленно эскалирует событие в UC6, минуя retry, так как повторная отправка без исправления данных или сертификата бессмысленна.
- **E2.** Превышен дневной лимит запросов к API оператора ЭДО (rate limiting). Hub переводит документ в очередь отложенной отправки с приоритетом на начало следующего расчётного окна.

### Постусловия
- **Успех:** документ имеет статус `Передан в СФР`, временная метка и номер попытки зафиксированы в журнале.
- **Неуспех после исчерпания retry:** документ имеет статус `Эскалирован`, кадровик уведомлён.

### Нефункциональные требования, связанные с UC3/UC5
- NFR-01: время от готовности документа до первой попытки отправки — не более 60 секунд (для событий с жёстким регуляторным сроком: приём, увольнение).
- NFR-02: журнал попыток должен храниться не менее срока хранения кадрового документа-основания, согласно архивному законодательству (см. [`requirements.md`](requirements.md); точный срок для технических логов уточняется на этапе проектирования хранилища).
- NFR-03: механизм retry должен быть идемпотентным — повторная отправка одного и того же документа не должна приводить к дублированию сведений в СФР (согласовать с оператором ЭДО уникальный idempotency-key на уровне пакета).

### Критерии приёмки (Gherkin-стиль)

```gherkin
Сценарий: Успешная отправка пакета с первой попытки
  Дано документ об увольнении прошёл валидацию
  Когда Hub отправляет пакет оператору ЭДО
  И оператор ЭДО принимает пакет без ошибок
  Тогда документ получает статус "Передан в СФР"
  И счётчик попыток равен 1

Сценарий: Технический сбой и успешный retry
  Дано первая попытка отправки завершилась таймаутом
  Когда проходит 5 минут
  Тогда Hub автоматически инициирует повторную отправку
  И при успехе документ получает статус "Передан в СФР"

Сценарий: Исчерпание попыток retry
  Дано документ уже прошёл 3 неудачные попытки отправки по техническим причинам
  Когда наступает время для 4-й попытки
  Тогда Hub не выполняет повторную отправку
  И документ получает статус "Эскалирован"
  И кадровый специалист получает уведомление

Сценарий: Содержательная ошибка не требует retry
  Дано оператор ЭДО вернул код 400 из-за истёкшего сертификата ЭЦП
  Когда Hub обрабатывает ответ
  Тогда retry не инициируется
  И документ немедленно получает статус "Эскалирован"
```

## UC4 + UC6 — Получить статус обработки от СФР (с эскалацией)

| Поле | Значение |
|---|---|
| **ID** | UC4 |
| **Название** | Получить статус обработки от СФР |
| **Уровень** | Пользовательская цель, реализуется системным актором |
| **Первичный актор** | HR Compliance Hub |
| **Вторичные акторы** | СФР (источник статуса), Оператор ЭДО (транзитное звено доставки webhook) |
| **Заинтересованные стороны и их интересы** | Кадровый специалист: не должен вручную проверять статус. Бухгалтерия: должна получать сигнал только после подтверждения. Compliance-офицер: должен видеть полную историю отклонений для отчётности перед ГИТ |

### Предусловия
- Документ имеет статус `Передан в СФР` (результат UC3).
- Hub подписан на webhook-канал оператора ЭДО для получения статусов (настроено на этапе интеграции, вне рамок данного UC).

### Триггер
Оператор ЭДО пересылает в Hub асинхронное уведомление о статусе, полученное от СФР (webhook callback).

### Основной поток событий

1. Hub получает webhook-уведомление о статусе документа от оператора ЭДО.
2. Hub сопоставляет уведомление с документом по уникальному идентификатору пакета (idempotency-key/correlation-id).
3. Hub проверяет тип статуса: **подтверждено**.
4. Hub присваивает документу статус `Подтверждён СФР`.
5. Hub публикует событие `TerminationConfirmedBySFR` в шину сообщений для подписчиков (HRM-система, система расчёта зарплаты).
6. Use case завершается успешно.

### Альтернативный поток A2 — статус «отклонено» по технической причине

- A2.1. Полученный статус — отклонение с кодом технической категории (например, «сервис СФР временно недоступен на момент обработки», «истёк таймаут обработки на стороне СФР»).
- A2.2. Управление передаётся в UC5 (повторная отправка) согласно BR-01.

### Альтернативный поток A3 — статус «отклонено» по содержательной причине

- A3.1. Полученный статус — отклонение с кодом содержательной категории (например, «СНИЛС не найден в реестре», «дублирующая запись о трудовой деятельности», «несоответствие ФИО данным реестра»).
- A3.2. Retry не инициируется (согласно BR-01, содержательные отклонения retry не подлежат).
- A3.3. Управление немедленно передаётся в UC6 (эскалация).

### Расширение UC6 — Эскалировать событие кадровику

*Активируется как `<<extend>>` UC4 при содержательном отклонении (A3) либо при исчерпании попыток retry после технического сбоя (см. UC5).*

1. Hub присваивает документу статус `Требует ручного вмешательства`.
2. Hub формирует уведомление, включающее: ФИО сотрудника, тип кадрового события, точный код и текст отклонения от СФР/оператора, количество уже предпринятых попыток (если применимо).
3. Hub отправляет уведомление кадровому специалисту (канал уведомления — согласно настройке: email, встроенный дашборд Hub, интеграция с корпоративным мессенджером — уточняется на этапе проектирования интерфейсов).
4. Событие одновременно становится видимым в журнале для Compliance-офицера (UC8) с пометкой «требует внимания».
5. Кадровый специалист вручную исправляет данные в HRM (вне границ системы Hub) и инициирует повторную отправку вручную — это **новый экземпляр UC1**, а не автоматический retry.

### Исключения

- **E3.** Webhook от оператора ЭДО получен, но не удаётся сопоставить с документом (некорректный или отсутствующий correlation-id). Hub помещает уведомление в «карантинную очередь» (dead-letter queue) и оповещает ИТ-администратора — это технический инцидент интеграции, а не бизнес-исключение.
- **E4.** Один и тот же статус получен повторно (дублирующийся webhook — распространённая ситуация при at-least-once delivery в message-брокерах). Hub проверяет идемпотентность по correlation-id + статусу и игнорирует дубликат без повторной публикации события `TerminationConfirmedBySFR`.

### Постусловия
- **Успех:** документ имеет статус `Подтверждён СФР`; событие подтверждения опубликовано ровно один раз (гарантия exactly-once на уровне бизнес-эффекта, даже при at-least-once на уровне транспорта).
- **Эскалация:** документ имеет статус `Требует ручного вмешательства`; кадровик и Compliance-офицер уведомлены.

### Нефункциональные требования, связанные с UC4/UC6

- NFR-04: время обработки входящего webhook от получения до публикации внутреннего события — не более 5 секунд (p95).
- NFR-05: система обязана обеспечивать идемпотентную обработку повторно доставленных webhook-уведомлений (защита от дублирования начислений/статусов).
- NFR-06: эскалационное уведомление кадровику должно быть доставлено не позднее 15 минут с момента классификации события как требующего ручного вмешательства — это регуляторно значимый SLA, так как от него зависит соблюдение срока подачи сведений в СФР.

### Критерии приёмки (Gherkin-стиль)

```gherkin
Сценарий: Успешное подтверждение от СФР
  Дано документ имеет статус "Передан в СФР"
  Когда Hub получает webhook со статусом "подтверждено"
  Тогда документ получает статус "Подтверждён СФР"
  И публикуется событие TerminationConfirmedBySFR

Сценарий: Содержательное отклонение эскалируется немедленно
  Дано документ имеет статус "Передан в СФР"
  Когда Hub получает webhook со статусом "отклонено" с содержательным кодом ошибки
  Тогда retry не инициируется
  И документ получает статус "Требует ручного вмешательства"
  И кадровый специалист получает уведомление в течение 15 минут

Сценарий: Дублирующийся webhook игнорируется
  Дано документ уже получил статус "Подтверждён СФР"
  Когда Hub повторно получает тот же самый webhook с тем же correlation-id
  Тогда статус документа не изменяется
  И событие TerminationConfirmedBySFR повторно не публикуется
```
