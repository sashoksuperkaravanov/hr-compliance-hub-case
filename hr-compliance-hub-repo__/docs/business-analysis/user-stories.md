# User Stories

**Связаны с:** UC8 (журнал статусов, Compliance-офицер) и UC9 (retry-политика, ИТ-администратор). По приоритизации MoSCoW эти два use case оставались неспецифицированными до API-контрактов.

---

## Эпик: Журнал статусов кадровых документов (UC8, FR-11, FR-13, NFR-08, NFR-10)

### US-01
**Как** Compliance-офицер,
**я хочу** видеть список всех кадровых документов холдинга с фильтрацией по статусу, площадке и периоду,
**чтобы** оперативно выявлять документы, застрявшие в статусе `requires_manual_intervention`, не дожидаясь плановой проверки.

**Критерии приёмки:**
```gherkin
Сценарий: Фильтрация по статусу "требует вмешательства"
  Дано я авторизован с ролью compliance_officer
  Когда я запрашиваю список документов со статусом requires_manual_intervention
  Тогда я вижу документы всех площадок холдинга с этим статусом
  И список отсортирован по updated_at (сначала самые старые)

Сценарий: Кадровик не видит документы чужой площадки
  Дано я авторизован с ролью hr_specialist, площадка А
  Когда я запрашиваю список документов без фильтра по площадке
  Тогда я вижу только документы площадки А
```

**Связанный эндпоинт:** `GET /v1/documents`
**Приоритет:** Should (MoSCoW)

---

### US-02
**Как** Compliance-офицер,
**я хочу** открыть карточку конкретного документа и увидеть полную историю его попыток отправки и изменений статуса,
**чтобы** при подготовке отчётности перед ГИТ иметь готовое обоснование каждого случая просрочки без ручного сведения данных из разных систем.

**Критерии приёмки:**
```gherkin
Сценарий: Просмотр истории попыток
  Дано документ прошёл 2 неудачные технические попытки и был подтверждён на 3-й
  Когда я открываю карточку документа
  Тогда я вижу все 3 попытки с временными метками, кодами ошибок первых двух
  И вижу итоговый статус confirmed_by_sfr

Сценарий: Журнал изменений статуса неизменяем
  Дано документ имеет 5 записей в журнале изменений статуса
  Когда я запрашиваю журнал повторно через час
  Тогда количество и содержание записей не изменилось (append-only, NFR-10)
```

**Связанные эндпоинты:** `GET /v1/documents/{documentId}`, `GET /v1/documents/{documentId}/attempts`, `GET /v1/documents/{documentId}/status-log`
**Приоритет:** Should

## Эпик: Настройка retry-политики (UC9, FR-12, BR-01)

### US-03
**Как** ИТ-администратор,
**я хочу** просматривать текущие параметры retry-политики (количество попыток, интервалы),
**чтобы** перед изменением понимать, какая конфигурация действует сейчас, и не вносить правки вслепую.

**Критерии приёмки:**
```gherkin
Сценарий: Просмотр действующей конфигурации
  Дано retry-политика не изменялась с момента внедрения (BR-01 по умолчанию)
  Когда я запрашиваю текущую конфигурацию
  Тогда я вижу max_attempts=3, интервалы 5/30/120 минут
```

**Связанный эндпоинт:** `GET /v1/config/retry-policy`
**Приоритет:** Could

---

### US-04
**Как** ИТ-администратор,
**я хочу** изменить параметры retry-политики без обращения к разработчикам,
**чтобы** оперативно реагировать на изменение нагрузки на API оператора ЭДО (например, увеличить интервалы при массовых технических сбоях) без внепланового релиза.

**Критерии приёмки:**
```gherkin
Сценарий: Успешное изменение конфигурации
  Дано я авторизован с ролью it_admin
  Когда я устанавливаю max_attempts=5 и увеличиваю интервалы вдвое
  Тогда создаётся новая версия конфигурации
  И предыдущая версия остаётся в истории (не удаляется)

Сценарий: Попытка изменения без прав
  Дано я авторизован с ролью hr_specialist
  Когда я пытаюсь изменить retry-политику
  Тогда я получаю ошибку 403

Сценарий: Изменение не затрагивает уже запланированные попытки
  Дано документ X ожидает 2-ю попытку через 15 минут по старой политике (интервал 30 мин)
  Когда ИТ-администратор меняет интервал на 60 минут
  Тогда попытка по документу X всё равно происходит через оставшиеся 15 минут,
    а не пересчитывается по новой политике
```

**Связанный эндпоинт:** `PUT /v1/config/retry-policy`
**Приоритет:** Could
**Примечание:** последний сценарий — прямое следствие решения «версионирование, не перезапись» из [`api-contracts-overview.md`](../../api/api-contracts-overview.md), раздел 3.2.
