# Функциональные и нефункциональные требования

**Проект:** HR Compliance Hub
**Версия:** 1.0 (консолидация после Context Diagram, до State/Sequence Diagram)

---

## 1. Функциональные требования (FR)

| ID | Требование | Связанный Use Case | Приоритет (MoSCoW) |
|---|---|---|---|
| FR-01 | Hub получает событие кадрового документа из HRM-системы через шину сообщений (асинхронно) | UC1 | Must |
| FR-02 | Hub валидирует данные документа (контрольная сумма СНИЛС, обязательные поля) до отправки во внешние системы | UC2 | Must |
| FR-03 | При обнаружении невалидных данных Hub немедленно уведомляет кадрового специалиста, не инициируя отправку в СФР | UC2, UC10 | Must |
| FR-04 | Hub формирует пакет документов в формате оператора ЭДО, включая усиленную квалифицированную электронную подпись организации | UC3 | Must |
| FR-05 | Hub выполняет автоматическую повторную отправку (retry) при технических сбоях согласно правилу BR-01 (3 попытки, интервалы 5 мин / 30 мин / 2 часа) | UC5 | Must |
| FR-06 | Hub классифицирует каждый отказ (от оператора ЭДО или СФР) как технический либо содержательный, используя код ошибки ответа | UC4, BR-01 | Must |
| FR-07 | Hub получает статус обработки документа от СФР асинхронно через webhook (транзитом от оператора ЭДО) | UC4 | Must |
| FR-08 | При содержательном отклонении или исчерпании попыток retry Hub эскалирует событие кадровому специалисту в пределах SLA (NFR-06) | UC6 | Must |
| FR-09 | После подтверждения СФР Hub публикует событие `TerminationConfirmedBySFR` для HRM-системы и системы расчёта зарплаты | UC7 | Must |
| FR-11 | Compliance-офицер может просматривать журнал статусов всех кадровых документов с фильтрацией по статусу, дате, площадке | UC8 | Should |
| FR-12 | ИТ-администратор может настраивать параметры retry-политики (количество попыток, интервалы) без изменения кода | UC9 | Could |
| FR-13 | Hub логирует каждую попытку отправки с указанием причины предыдущей неудачи, доступную для просмотра Compliance-офицером | UC5, BR-01 | Must |

> **Примечание:** FR-10 удалён из перечня как дублирующий NFR-05 (идемпотентная обработка webhook) практически дословно. Идемпотентность — качественный атрибут реализации FR-01/FR-07, а не отдельная бизнес-функция, и остаётся только в NFR-05.

## 2. Нефункциональные требования (NFR)

| ID | Категория | Требование | Обоснование / источник |
|---|---|---|---|
| NFR-01 | Производительность | Время от готовности документа до первой попытки отправки — не более 60 секунд для событий с жёстким регуляторным сроком (приём, увольнение) | Регуляторный срок ЕФС-1: рабочий день, следующий за приказом (п. 2 ст. 11 ФЗ-27); минимальный запас перед сроком |
| NFR-02 | Хранение данных | Журнал попыток отправки (`DeliveryAttempt`, `StatusChangeLog`) хранится не менее срока хранения самого кадрового документа-основания, согласно архивному законодательству (Федеральный закон № 125-ФЗ «Об архивном деле», Перечень типовых архивных документов, утв. Приказом Росархива) | Срок хранения кадровых документов регулируется архивным законодательством, а не сроком исковой давности по трудовым спорам (ст. 392 ТК РФ, 1 месяц по спорам об увольнении, 1 год по невыплаченным суммам) — последний слишком короток для этой цели. Открытый вопрос: относятся ли `DeliveryAttempt`/`StatusChangeLog` к тому же архивному сроку, что и сам приказ, или это отдельная категория с более коротким сроком. Требует решения на этапе проектирования хранилища |
| NFR-03 | Целостность данных | Механизм retry идемпотентен: повторная отправка одного документа не создаёт дублирующих сведений в СФР (уникальный idempotency-key на уровне пакета) | Use Case Spec UC3/UC5 |
| NFR-04 | Производительность | Время обработки входящего webhook от получения до публикации внутреннего события — не более 5 секунд (p95) | Use Case Spec UC4 |
| NFR-05 | Целостность данных | Идемпотентная обработка повторно доставленных webhook (at-least-once delivery на уровне транспорта не должна приводить к дублированию бизнес-эффекта) | Use Case Spec UC4, исключение E4 |
| NFR-06 | Время реакции | Эскалационное уведомление кадровику доставляется не позднее 15 минут с момента классификации события как требующего вмешательства | Регуляторно значимый SLA, влияет на соблюдение срока подачи в ЕФС-1 |
| NFR-07 | Безопасность | Взаимодействие с API оператора ЭДО аутентифицируется сертификатом усиленной квалифицированной ЭП; Hub отслеживает срок действия сертификата и предупреждает за 30 дней до истечения | Предотвращение исключения E1 (Use Case Spec UC3) |
| NFR-08 | Контроль доступа | Доступ к журналу статусов (UC8) разграничен по ролям (RBAC): полный доступ — Compliance-офицер/аудитор, доступ только к своим документам — кадровый специалист | Комплаенс-требование к персональным данным (152-ФЗ) |
| NFR-09 | Отказоустойчивость | Доступность Hub — не менее 99.5% в рабочие часы (события с жёстким регуляторным сроком не должны теряться при кратковременной недоступности сервиса) | Регуляторная критичность процесса |
| NFR-10 | Аудируемость | Все изменения статуса документа записываются в неизменяемый (append-only) журнал с указанием инициатора (система/пользователь) и временной метки | Требование внутреннего аудита, п. 4 карты стейкхолдеров |
