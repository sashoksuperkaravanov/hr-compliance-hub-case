## 2. Новые сценарии (закрывают пробелы Traceability Matrix)

### TS-16 — Технический сбой самой отправки оператору ЭДО

```gherkin
Сценарий: Таймаут при вызове API оператора ЭДО (не ответ СФР, а сбой самого вызова)
  Дано документ прошёл валидацию и готов к отправке
  Когда Hub вызывает API оператора ЭДО для отправки пакета
  И вызов завершается таймаутом (оператор недоступен)
  Тогда Hub классифицирует это как технический сбой (FR-06)
  И документ получает статус "retry_scheduled"
  И это НЕ засчитывается как ответ от СФР — Catch_2 не срабатывает

Сценарий: Успешное завершение после сбоя отправки
  Дано первая попытка отправки завершилась таймаутом на стороне оператора
  Когда наступает время повторной попытки (5 минут)
  И повторный вызов оператора ЭДО завершается успехом
  Тогда документ переходит в статус "transit_to_sfr"
  И счётчик попыток равен 2
```

**Отличие от TS-02:** TS-02 покрывает технический сбой как отклонение, пришедшее *от СФР* через `Gateway_Status`. TS-16 проверяет отдельную ветку `Gateway_SendResult`, добавленную в BPMN/Sequence после уточнения логики на этапе тестового покрытия: до появления этой ветки протестировать данный случай было невозможно, поскольку в диаграммах он не был выделен отдельно.

### TS-17 — Содержательная ошибка при отправке (невалидный сертификат ЭЦП)

```gherkin
Сценарий: Оператор ЭДО немедленно отклоняет пакет из-за истёкшего сертификата
  Дано сертификат ЭЦП организации истёк
  Когда Hub вызывает API оператора ЭДО для отправки пакета
  И оператор возвращает код 4xx с указанием на невалидную подпись
  Тогда retry НЕ инициируется
  И документ немедленно получает статус "requires_manual_intervention"
  И кадровый специалист получает уведомление в течение 15 минут (NFR-06)
```

### TS-18 — Уведомление кадровика при невалидных данных (UC10 отдельно от общего потока)

```gherkin
Сценарий: Невалидный СНИЛС не проходит контрольную сумму
  Дано документ содержит СНИЛС, не проходящий контрольную сумму
  Когда Hub выполняет валидацию (UC2)
  Тогда попытка отправки оператору ЭДО НЕ инициируется
  И кадровый специалист получает уведомление об ошибке немедленно
  И документ получает статус "requires_manual_intervention"
  И это НЕ считается технической или содержательной ошибкой ОТПРАВКИ:
    ошибка обнаружена до попытки отправки
```

### TS-19 — Предупреждение об истекающем сертификате ЭЦП (частичное покрытие NFR-07)

```gherkin
Сценарий: Сертификат истекает через 25 дней
  Дано срок действия сертификата ЭЦП организации истекает через 25 дней
  Когда наступает ежедневная проверка сроков действия сертификатов
  Тогда ИТ-администратор получает предупреждение (NFR-07: за 30 дней до истечения)
```

**Примечание:** это единственный сценарий, покрывающий NFR-07 на уровне Gherkin. Сама отправка с истёкшим сертификатом уже покрыта TS-17.

## 3. Нефункциональные требования без Gherkin-покрытия

Следующие NFR не могут быть адекватно проверены сценарным Gherkin-тестом, им нужен иной вид проверки. Ниже — не тест-кейсы, а зафиксированный подход к проверке каждого из них:

| NFR | Требование | Как проверяется (не Gherkin) |
|---|---|---|
| NFR-01 | Первая попытка ≤60 сек | Нагрузочный тест: замер времени от публикации события HRM до первого вызова оператора ЭДО, под реалистичной нагрузкой (пиковая — массовое сокращение на площадке) |
| NFR-02 | Срок хранения логов | Проверка конфигурации политики хранения в БД/архивном хранилище, не функциональный тест |
| NFR-04 | Обработка webhook ≤5 сек p95 | Нагрузочный тест с измерением перцентилей времени ответа |
| NFR-06 | Эскалация ≤15 мин | Интеграционный тест с реальным таймером, не unit/Gherkin |
| NFR-09 | Доступность 99.5% | SLA-мониторинг в продакшене (uptime-трекер), не предрелизный тест |

Эти пять NFR требуют отдельного плана нагрузочного и SLA-тестирования — артефакта, которого пока не существует в проекте.

## 4. Итог покрытия

Из 19 тест-сценариев (TS-01…TS-19): 15 существовали ранее, 4 добавлены на этом шаге для закрытия пробелов, обнаруженных при сборке Traceability Matrix. Из 10 NFR — 5 покрыты Gherkin-логикой (прямо или косвенно), 5 требуют нефункционального тестирования вне рамок Gherkin (раздел 3).

Не закрыто данным шагом: UC1, UC2, UC7 всё ещё не имеют собственной Use Case Specification, поэтому для них пока нет формального acceptance-критерия сверх того, что уже покрыто TS-18 (частично для UC2 через UC10-ветку).
